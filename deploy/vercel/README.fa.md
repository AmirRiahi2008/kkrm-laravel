# استقرار نسخهٔ Blade روی Vercel

پروژهٔ جدید: `kkrm-laravel` در تیم `amirrezas-projects-4fd6211a`.
پروژهٔ قبلی `kkrm` تغییر نکرده است.

این نسخه از Container Runtime ورسل استفاده می‌کند. فایل `Dockerfile.vercel` دارایی‌ها را با Node 22 می‌سازد و برنامه را با PHP 8.4 و Apache روی پورت 80 اجرا می‌کند. Node فقط در مرحلهٔ ساخت استفاده می‌شود. نصب Composer مطابق lock است و هیچ مهاجرت یا سیدری در build یا startup اجرا نمی‌شود.

## پیش‌نیاز اتصال داده

در Settings → Environment Variables پروژهٔ جدید، برای Preview اطلاعات دیتابیس MySQL آزمایشی را وارد کنید:

- `DB_HOST`: میزبان خارجی قابل دسترس از ورسل؛ localhost معتبر نیست.
- `DB_PORT`: پورت واقعی سرویس.
- `DB_DATABASE`: نام دیتابیس آزمایشی.
- `DB_USERNAME`: کاربر محدود همان دیتابیس.
- `DB_PASSWORD`: رمز، از نوع Secret.

برای فایل‌های آپلودی، یک bucket خصوصی سازگار با S3 لازم است:

- `AWS_ENDPOINT`: آدرس HTTPS سرویس S3، برای AWS اصلی می‌تواند خالی بماند.
- `AWS_BUCKET`: نام bucket.
- `AWS_DEFAULT_REGION`: منطقهٔ سرویس.
- `AWS_ACCESS_KEY_ID` و `AWS_SECRET_ACCESS_KEY`: از نوع Secret، با دسترسی محدود به همان bucket.
- `AWS_USE_PATH_STYLE_ENDPOINT`: برای سرویس‌های سازگار معمولاً true، برای AWS مطابق سرویس تنظیم شود.

`APP_KEY` جدا برای Preview و Production ساخته شده است. در صورت اتصال دیتابیس واقعی به‌جای محیط آزمایشی، کلید واقعی همان برنامه باید جایگزین شود. مقدار کلید یا رمزها را در چت، Git، فایل ZIP یا متغیر VITE قرار ندهید.

## راه‌اندازی داده

مایگریشن‌ها یک‌بار روی دیتابیس مقصد، از دستگاه یا محیطی با دسترسی PHP و همان متغیرها اجرا می‌شوند:

```bash
php artisan migrate --force
php artisan db:seed --class=SiteStructureSeeder --force
php artisan app:create-admin admin@example.com
```

SiteStructureSeeder فقط برای دیتابیس تازه است؛ برای دیتابیس واردشدهٔ موجود بدون بررسی دوباره اجرا نشود. DemoSeeder روی production اجرا نشود. رمز مدیریت با ورودی پنهان فرمان تنظیم می‌شود.

فایل‌های خصوصی فعلی برای انتقال باید در همان مسیر نسبی درج‌شده در `media.path` به bucket منتقل شوند. مقادیر `media.disk` رکوردهای منتقل‌شده نیز باید پس از پشتیبان‌گیری و تأیید نسخهٔ جدید با disk مقصد سازگار شوند؛ تغییر MEDIA_DISK به‌تنهایی عکس‌های قبلی را منتقل نمی‌کند.

## تنظیمات اجرا

- Framework: Container
- Root Directory: ریشهٔ نسخهٔ Laravel Blade
- Region: fra1
- Install / Build Command / Output Directory: تنظیم جدا لازم نیست؛ Dockerfile مسئول ساخت است.
- Preview از VERCEL_URL برای APP_URL، FRONTEND_URL و دامنهٔ Sanctum استفاده می‌کند.
- برای Production با دامنهٔ اختصاصی، APP_URL را آدرس HTTPS نهایی قرار دهید.
- Session و cache روی دیتابیس‌اند؛ فایل‌های کاربر روی S3 هستند.
- لاگ در stderr است و از Runtime Logs ورسل قابل مشاهده است.
- صف برای این استقرار sync است؛ worker دائمی Supervisor روی ورسل راه‌اندازی نمی‌شود.
- بازیابی رمز تا تنظیم سرویس ایمیل واقعی تنها در لاگ ثبت می‌شود؛ از فعال بودن ایمیل در production مطمئن شوید.

ورسل محدودیت payload دارد. این تنظیمات حداکثر فایل را ۳۸۴۰ کیلوبایت قرار می‌دهند تا multipart نیز زیر محدودیت درخواست بماند. برای PDF بزرگ‌تر باید ارسال مستقیم به فضای فایل، اعتبارسنجی سمت سرور و ثبت نهایی امن جداگانه پیاده شود؛ افزایش MEDIA_MAX_KB محدودیت ورسل را برطرف نمی‌کند.

شروع کانتینر در صورت نبود APP_KEY، اطلاعات MySQL یا تنظیم disk دائمی متوقف می‌شود تا استقرار ناقص به‌اشتباه آماده تلقی نشود.

## بررسی پس از استقرار

صفحهٔ اصلی، `/en`، `/experts`، جزئیات خبر، فایل‌های رسانه، `/admin/login`، ورود و خروج، ایجاد/ویرایش خبر، انتخاب اسلایدشو، تصویر و PDF، آلبوم و تقویم شمسی باید با دیتابیس و bucket مقصد بررسی شوند. حالت READY در ورسل فقط تکمیل build است و تأیید سلامت تمام صفحات نیست.

تنظیم اعتماد عمومی به تمام proxyها اعمال نشده است. Apache در این کانتینر HTTPS را ثابت در نظر می‌گیرد، چون TLS در ورودی Vercel خاتمه می‌یابد؛ از X-Forwarded-Proto دلخواه کاربر استفاده نمی‌کند. شناسایی IP واقعی برای محدودیت‌های مبتنی بر IP باید روی محیط مقصد با هدرهای مستند Vercel تأیید شود؛ تا آن زمان TRUSTED_PROXIES خالی می‌ماند.
