# بررسی عکس‌ها و انتقال به فضای دائمی

در commit جدید `37fc3fcd0091e2a62e2254decb5807af2871545c`، تعداد ۲۳ تصویر WebP به `storage/app/public/media` اضافه شده است. این فایل‌ها در اصلاحات حفظ شده‌اند. ریشهٔ public با ریشهٔ private یکی نیست؛ هر فایل باید با disk و path رکورد خودش تطبیق داشته باشد. مسیر این ۲۳ فایل در بکاپ SQL قبلیِ بررسی‌شده وجود نداشت، بنابراین برای تطبیق آن‌ها باید دیتابیس مربوط به همین فایل‌ها را بررسی کرد؛ نام فایل‌ها را حدسی به رکوردهای قبلی متصل نکنید.

## چه چیزی در سورس اصلاح شده است؟

- در commit مبنای گیت‌هاب، `resources/views/.gitignore` همهٔ قالب‌ها را حذف کرده بود. ۳۶ فایل قالب بازیابی شده‌اند و ignore آن پوشه اصلاح شده است.
- مسیر `/api/v1/media/{id}` از گروه web لاراول استفاده می‌کند تا کوکی رمزگذاری‌شده و نشست مدیر را حتی در درخواست تصویر بدون Origin و Referer دریافت کند. عکس‌های پیش‌نویس یا فایل‌های استفاده‌نشده همچنان برای مهمان 404 هستند. فایل‌های منتشرشده برای مهمان قابل نمایش‌اند.
- مسیر قدیمی `/backend/api/v1/media/{id}` حفظ شده است.
- لینک عکس و PDF داخل HTML، فقط برای دامنهٔ فعلی و دامنه‌های شناخته‌شدهٔ قبلی، به مسیر نسبی همین سایت تبدیل می‌شود. آدرس عکس‌های سایت‌های دیگر دست‌نخورده می‌ماند. دامنه‌های دیگرِ قبلی را با کاما در `MEDIA_LEGACY_ORIGINS` اضافه کنید.
- دستورهای بررسی و انتقال، با مسیر نسبی و کنترل SHA-256 کار می‌کنند. فایل اصلی حذف نمی‌شود و فایل متفاوت مقصد نیز بازنویسی نمی‌شود.

## ۱. بررسی محلی

از پوشه‌ای که `artisan` داخل آن است اجرا کنید:

```bash
php artisan config:clear
php artisan view:clear
php artisan media:audit --verify
```

`Ready` یعنی فایل در دیسک همان رکورد وجود دارد و، با `--verify`، اندازه و هش آن نیز صحیح است. `Missing` یعنی در محل مورد انتظار نیست. ستون آخر ریشه‌های دیگری را که همان مسیر نسبی در آن‌ها پیدا شده نشان می‌دهد. `Invalid` می‌تواند به معنی خرابی فایل، دسترسی فایل یا تنظیمات دیسک باشد. فرمان هیچ تغییری اعمال نمی‌کند و در صورت مشکل exit code برابر 1 برمی‌گرداند.

برای بررسی یک عکس:

```bash
php artisan media:audit --id=169 --verify
```

اگر رکورد آن `disk=local` و `path=media/2026/10/example.jpg` باشد، مسیر فایل باید این باشد:

```text
storage/app/private/media/2026/10/example.jpg
```

قرار داشتن فایل در `storage/media` یا `storage/app/public/media` با این تنظیمات یکسان نیست. `storage:link` نیز مسیر private را جابه‌جا نمی‌کند.

## ۲. اصلاح فایل‌هایی که در پوشهٔ دیگری هستند

پیش از اعمال انتقال از دیتابیس پشتیبان بگیرید. اگر گزارش نشان داد فایل‌های رکوردهای local داخل `storage/app/public/media` هستند، ابتدا بررسی کنید:

```bash
php artisan media:transfer --from=local --to=local --source-root="storage/app/public"
```

این دستور dry run است. فقط اگر فایل‌ها و هش آن‌ها درست باشند، همان فرمان را با `--apply` اجرا کنید:

```bash
php artisan media:transfer --from=local --to=local --source-root="storage/app/public" --apply
php artisan media:audit --verify
```

دستور فایل‌ها را در مسیر private مورد انتظار کپی می‌کند. فایل‌های منبع باقی می‌مانند. `--source-root` باید پوشهٔ **والد media** باشد، نه خود پوشهٔ media. برای مسیری خارج پروژه، آدرس کامل آن را داخل کوتیشن بگذارید. اگر فقط چند رکورد مشکل دارند، به هر دو فرمان گزینه‌هایی مثل `--id=169 --id=170` اضافه کنید.

اگر می‌خواهید همان پوشهٔ قدیمی، ریشهٔ local باقی بماند، به‌جای کپی می‌توانید `MEDIA_LOCAL_ROOT` را در `.env` به مسیر مطلق والد media تنظیم و `php artisan config:clear` اجرا کنید. این گزینه برای اجرای روی هاست دارای دیسک دائمی است؛ در Vercel آپلودهای جدید باید روی S3 باشند.

وجود فایل هم‌نام کافی نیست؛ اگر اندازه یا SHA-256 با رکورد تفاوت داشته باشد، انتقال متوقف می‌شود. عکس اصلی را از بکاپ صحیح بازیابی کنید و هش دیتابیس را صرفاً برای عبور از این بررسی عوض نکنید.

## ۳. انتقال عکس‌های فعلی به S3 برای Vercel

بستهٔ SQL و Git عکس‌های آپلودشده را همراه خود ندارند. روی دستگاهی که **فایل‌های اصلی** وجود دارند، تنظیمات `DB_*` را به دیتابیس مقصد متصل و تنظیمات `AWS_*` را طبق [راهنمای ورسل](../deploy/vercel/README.fa.md) در `.env` وارد کنید. این فایل را commit نکنید.

پس از backup دیتابیس مقصد، ابتدا dry run و بعد انتقال واقعی:

```bash
php artisan config:clear
php artisan media:transfer --from=local --to=s3
php artisan media:transfer --from=local --to=s3 --apply
php artisan media:audit --verify
```

هر فایل ابتدا در مقصد بررسی یا کپی و سپس دوباره خوانده می‌شود. فقط پس از تأیید اندازه و هش، `media.disk` همان رکورد به s3 تغییر می‌کند. `media.path` ثابت می‌ماند. فایل‌های اصلی حذف نمی‌شوند. اگر انتقال بخشی از فایل‌ها شکست خورد، پس از رفع مشکل دوباره فرمان را اجرا کنید؛ رکوردهای قبلاً منتقل‌شده دوباره انتخاب نمی‌شوند.

اگر رکوردهایی با disk=public دارید، برای آن‌ها نیز جدا اجرا کنید:

```bash
php artisan media:transfer --from=public --to=s3
php artisan media:transfer --from=public --to=s3 --apply
```

اگر فایل‌های local در مسیر دیگری از بکاپ هستند، `--source-root` را به هر دو فرمان اضافه کنید. تغییر `MEDIA_DISK=s3` به‌تنهایی فایل‌های قدیمی و ستون disk آن‌ها را منتقل نمی‌کند. بعد از پایان انتقال، برای آپلودهای بعدی `MEDIA_DISK=s3` باشد.

## ۴. بررسی نمایش

شناسهٔ یک فایل موجود را از گزارش بردارید و روی دامنهٔ همان برنامه باز کنید:

```text
/api/v1/media/169
```

- برای تصویری که در مطلب منتشرشده استفاده شده، پاسخ باید 200 و Content-Type تصویر باشد.
- برای تصویر تازهٔ استفاده‌نشده، ابتدا وارد داشبورد شوید و همان مسیر را باز کنید؛ مهمان نباید فایل خصوصی را ببیند.
- برای 404، وجود و حذف‌نشدن رکورد، `media:audit` و وضعیت انتشار محتوا را بررسی کنید.
- برای 500، `storage/logs` در هاست معمولی یا Runtime Logs در Vercel را بررسی کنید.

پس از تغییر تنظیمات یا جابه‌جایی فایل‌ها، صفحه را با کش غیرفعال تازه‌سازی کنید. عکس‌هایی که فایل اصلی‌شان موجود نیست با تغییر کد بازسازی نمی‌شوند.
